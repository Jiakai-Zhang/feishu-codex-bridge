# v0.3.1-beta.1 — Desktop 连续守护与 v0.2 安全迁移

这是 Windows / Codex 专用 Session Relay 的维护测试版。它修复 `v0.2.0-beta.1` 在持久化 Desktop relay pointer 后可能因 App Server 未启动而阻塞 Codex Desktop 的高影响问题，并把 `v0.3.0-beta.1` 的“登录时恢复一次”升级为连续 watchdog。

## 受影响范围

- `v0.2.0-beta.1`：`CODEX_APP_SERVER_WS_URL` 会直接持久化；系统重启或 App Server 退出后，Codex Desktop 可能报 `connect ECONNREFUSED 127.0.0.1:<port>` 并无法进入主界面。
- `v0.3.0-beta.1`：已增加登录恢复与 fail-open bootstrap，但登录任务只执行一次；登录后 App Server 再次退出时，仍存在 Desktop 随后重启而连接失败的窗口。
- 已自建 watchdog/guardian 的用户：可以升级。新版只读识别可能的自建进程、计划任务和 Windows 服务，不会停止、删除、重命名或覆盖它们。

## 连续 fail-open watchdog

- 新的当前用户任务名为 `FeishuCodexBridge-DesktopRelay-Watchdog`，登录后常驻，默认每 3 秒检查共享 App Server。
- 监听器消失时，watchdog 先撤销 Bridge-owned Desktop pointer，再尝试恢复 App Server；只有 PID、Codex 可执行文件、`app-server` 命令行和目标端口全部验证后才恢复 pointer。
- 官方 watchdog 使用按端口命名的单实例 mutex；重复启动不会产生第二个官方守护。
- activation state 精确记录 Bridge 拥有的 URL。稳定 bootstrap 不再把任意 loopback `/rpc` 地址都视为 Bridge 所有，避免清理其他本机集成。
- 激活必须验证计划任务、pointer 和同一 activation 的 ready heartbeat；严格 Doctor 还要求 heartbeat 新鲜且监听器由配置中的 Codex App Server 进程持有。
- 登录时的 Bridge 恢复改为异步启动，不会阻塞 App Server 的连续 heartbeat。

## 自建守护兼容策略

- 激活时会检查可能的自建守护类别，但输出不包含任务名、命令行或本机路径。
- 自建守护始终保留。官方 watchdog 会复用同一配置、同一 Codex 可执行文件启动的已验证 App Server，不会终止其进程。
- 两个守护恰好同时恢复时，端口校验与官方启动 mutex 会阻止两个官方实例；若自建守护先恢复成功，下一轮检查会直接复用它。
- 建议升级后先运行 `doctor.ps1 -RequireRunning -RequireDesktopRelay`。只有严格检查通过后，再由用户自行决定是否撤销旧守护；升级器不会代替用户清理。

## 升级保证

- `update.ps1` 仍保留配置、DPAPI 密文、群绑定、Session 设置、队列、输入账本、投递状态和恢复备份。
- 若升级前 Desktop relay 已启用，连续 watchdog 与严格 Desktop relay Doctor 现在是升级成功条件；失败会进入原有回滚流程。
- 升级器 smoke 覆盖 `v0.2` 风格的已启用 pointer 与严格 relay 检查；本机兼容测试另行创建了无害的模拟自建计划任务，并验证激活器只检测、不删除。
- pointer 保持不变且 Codex Desktop 当前正常时，无需仅因本次代码升级重启 Desktop。

## v0.2 已无法启动 Desktop 时

无需先启动 Codex Desktop。在旧安装目录的 PowerShell 中执行：

```powershell
.\configure-codex-desktop-relay.ps1 -Disable
.\update.ps1 -Version v0.3.1-beta.1 -StartBridge
.\configure-codex-desktop-relay.ps1
.\doctor.ps1 -RequireRunning -RequireDesktopRelay
```

随后完全退出并重新打开 Codex Desktop。若升级预检因脏工作树等原因停止，旧 pointer 已保持禁用，因此 Desktop 仍可使用内置 App Server 启动。

对应的 Agent Prompt：

```text
请按照 https://github.com/ninmon/feishu-codex-bridge/releases/tag/v0.3.1-beta.1 的恢复与升级说明处理这台 Windows 电脑。当前旧版可能因 CODEX_APP_SERVER_WS_URL 指向没有监听的本机端口而使 Codex Desktop 报 ECONNREFUSED。先只读确认当前 tag、安装目录、git status、pointer 和端口；若确认是 v0.2 的该故障，先运行旧版 configure-codex-desktop-relay.ps1 -Disable，让 Desktop fail open，再使用 update.ps1 -Version v0.3.1-beta.1 -StartBridge。保留全部本机配置、DPAPI 密文、绑定和投递状态，不得清理工作树，也不得停止或删除用户自建守护。升级后重新激活新版 watchdog，并以 doctor.ps1 -RequireRunning -RequireDesktopRelay 验证。
```

## 验证

- Node 全量测试：238/238 通过。
- Windows updater smoke 覆盖升级、状态保留、严格 relay 检查和失败回滚。
- 自建守护兼容测试验证模拟计划任务会被检测并保留，测试任务随后按精确名称撤销。

## Beta 限制

- 仅支持 Windows 与 Codex Desktop。
- 依赖 Codex App Server 的实验性 WebSocket 接口；Bridge 把外部 App Server 的生命周期视为自己的责任，不假设 Desktop 会替它启动或持续保活该进程。
- watchdog 能保证新启动的 Desktop 在监听器不可恢复时回退；已经连接的 Desktop 在 App Server 突然退出时是否能无缝重连，仍取决于 Codex Desktop 客户端行为。
- 当前 Project Agent/多人协作实现仍未纳入稳定发布合同。
